# context-curation 설치 및 사용

## 1. 설치 위치

opencode는 다른 구성요소와 마찬가지로 **단수형 디렉토리**를 씁니다
(`.opencode/agent/`, `.opencode/command/`, `.opencode/skill/`).

**프로젝트 전용:**
```
<프로젝트>/.opencode/skill/context-curation/
```

**모든 프로젝트에서 공용 (권장):**
```
~/.config/opencode/skill/context-curation/
```

이 스킬은 프로젝트마다 다시 만들 이유가 없으므로 전역 설치가 낫습니다.
압축을 풀어 폴더째로 복사하면 끝입니다.

```bash
unzip context-curation.zip -d ~/.config/opencode/skill/
opencode
```

설치 확인은 새 세션에서 `/skills` 또는 에이전트에게 "context-curation 스킬 있어?"로 하면 됩니다.

### 슬래시 커맨드도 같이 설치 (GLM 5.2 환경에서는 권장)

`command/tune-docs.md`를 커맨드 디렉토리에 복사하면 `/tune-docs`로 명시 호출할 수 있습니다.

```bash
cp ~/.config/opencode/skill/context-curation/command/tune-docs.md \
   ~/.config/opencode/command/tune-docs.md
```

스킬 자동 트리거는 모델이 description을 보고 "이 스킬을 읽어야겠다"고 판단해야 작동합니다.
Claude 계열은 이게 꽤 안정적인데, 오픈웨이트 모델은 편차가 큽니다. 명시 커맨드가 있으면
자동 트리거가 안 될 때의 대비책이 되고, 자동 트리거가 잘 되면 그냥 안 쓰면 됩니다.

## 2. 기존 셋업에 연결하기

현재 구성이 이렇게 되어 있다고 가정했습니다. 다르면 알려주세요.

```
<프로젝트>/
├── AGENTS.md              ← session-context-init 이 생성
├── plan.md                ← session-context-init 이 생성
└── docs/
    ├── handoff.md         ← session-handoff 가 매 세션 갱신
    ├── session-log.md     ← session-handoff 가 append (## Session NNN 헤딩)
    ├── decisions.md       ← session-handoff 가 append
    └── .curation-state.json   ← 이 스킬이 관리 (신규)
```

`integration/` 폴더의 세 파일이 연결 부분입니다.

0. **`session-handoff` 스킬에 한 줄 추가** (제일 중요). `docs/handoff-spec.md`가 있으면
   그걸 읽고 따르라는 지시입니다. 이 한 줄이 있어야 큐레이션이 handoff의 동작을 바꿀 수
   있습니다. 전문은 `integration/session-handoff-snippet.md`에 있습니다.
1. **`agents-md-snippet.md`** — AGENTS.md 포인터 표에 한 줄 추가.
   description만으로도 트리거되긴 하지만, L0에 포인터가 있으면 훨씬 안정적입니다.
2. **`session-handoff-snippet.md`** — 기존 handoff 스킬에 두 가지 추가:
   세션 로그에 `[candidate]` / `[gotcha]` / `[decision]` 태그를 달게 하는 것과,
   핸드오프 끝에서 큐레이션이 필요한지 판단해 **제안만** 하게 하는 것.
   이 두 개가 있어야 "사고 난 뒤에" 말고 "주기적으로" 돌아갑니다.
   세션 로그 헤딩은 `## Session NNN` 형태를 유지해 주세요. 스크립트가 이걸로 세션 수와
   미수확 구간을 셉니다.
3. **`README-integration.md`** — 세 조각이 어떻게 맞물리는지 그림.

첫 실행 전에 상태 파일을 만들어 두세요. 없으면 최근 5세션만 읽고 시작합니다.

```bash
mkdir -p docs
cp ~/.config/opencode/skill/context-curation/templates/curation-state.json \
   docs/.curation-state.json
# 안의 YYYY-MM-DD와 세션 번호를 현재 값으로 수정
```

### 공유 파일 정책

큐레이션은 **프로젝트 디렉토리 밖에 아무것도 쓰지 않습니다.**

| 변경 성격 | 대상 | 적용 주체 |
|---|---|---|
| 이 프로젝트 전용 (문서 집합, 주기, 필드) | `docs/handoff-spec.md` | 큐레이션 (승인 후) |
| 일반화 가능 (모든 프로젝트가 원할 개선) | 제안서 섹션 G에 메모만 | **EK 님이 직접** |

전역 handoff 스킬을 여러 프로젝트가 공유하는 이상, 그 파일은 다른 프로젝트들을 함께 고려한
사람이 판단해서 바꿔야 합니다. 한 프로젝트의 튜닝 실행에서 부수적으로 바뀌면, 증거는 그
프로젝트 하나 폭이고 검토자는 그 프로젝트 문서만 보고 있는 상태가 됩니다. 게다가 전역 파일
수정은 어느 프로젝트 기록에도 흔적이 안 남아서 나중에 복원이 안 됩니다.

섹션 G는 그래서 **실행 항목이 아니라 메모**입니다. 무엇을 관찰했는지, 왜 일반적으로 보이는지,
원하시면 넣을 정확한 문구. 적용은 EK 님 몫입니다.

`session-handoff`가 프로젝트 로컬(`.opencode/skill/`)에 있다면 이 구분이 사라집니다.
전부 프로젝트 범위이고 spec 파일도 선택사항이며, SKILL.md를 직접 고쳐도 됩니다.

## 3. 사용법

명시적으로 부르는 경우:

```
AGENTS.md가 너무 커진 것 같아. context-curation 스킬로 문서 레이어 정리해줘.
```

또는 그냥 상황만 말해도 트리거되도록 description을 써 두었습니다:

```
에이전트가 자꾸 같은 걸 까먹어. 문서 구조 좀 손봐줘.
M2 마일스톤 끝났으니 문서 정리하자.
```

에이전트는 감사 → 수확 → 분류 → 제안 순으로 진행하고
`docs/_tuning-proposal.md`를 쓴 뒤 **멈춥니다.** 승인 전에는 아무것도 안 고칩니다.
제안서를 읽고 항목별로 승인/거부하면 그때 적용합니다.

## 4. 감사 스크립트 단독 실행

스킬 없이 현황만 보고 싶을 때:

```bash
python .opencode/skill/context-curation/scripts/docs_inventory.py --root .
```

표준 라이브러리만 쓰고 네트워크 접근이 없어서 사내망에서 그대로 돕니다.
Python 3.8 이상이면 됩니다.

주요 옵션:

| 옵션 | 기본값 | 의미 |
|---|---|---|
| `--l0-budget` | 2000 | AGENTS.md 토큰 상한 |
| `--l1-budget` | 1500 | plan.md / handoff.md 상한 |
| `--stale-days` | 90 | 이보다 오래된 문서를 의심 대상으로 표시 |
| `--dup-threshold` | 0.45 | 문단 중복 판정 유사도 (0~1) |
| `--json` | | 사람 대신 에이전트가 읽을 형식 |

토큰 수치는 문자 수 기반 **추정치**입니다(한글은 1.5자/토큰, ASCII는 4자/토큰 가정).
±20% 정도로 보시면 되고, 절대값보다 추세를 보는 용도입니다.
사내 모델의 실제 토크나이저와는 다르므로, 정확한 값이 필요하면
`estimate_tokens()` 함수만 사내 토크나이저로 바꿔 끼우면 됩니다.

## 5. 토큰이 넉넉한 환경에서

희소 자원이 토큰에서 **검토 시간**으로 바뀝니다. 그에 맞춰 조정한 부분:

- **전체 이력을 태그로 훑고, 본문은 선별해서 읽습니다.** 승격 기준 중 "재발생"은 전체 이력을
  봐야 판정되지만, 전체 **커버리지**가 전체 **정독**을 요구하진 않습니다. 먼저
  `grep "\[candidate\]\|\[gotcha\]\|\[decision\]"`로 로그 전체를 훑으면 세션 2·9·14에
  걸친 사실도 잡히고, 그다음 히트 주변과 미수확 구간만 본문을 읽습니다.
  로그가 작으면(감사 리포트가 % 로 알려줍니다) 그냥 다 읽는 게 최선입니다.
- **노후 문서를 실제로 검증**합니다. 수정 시각으로 의심만 하고 사용자에게 묻는 대신,
  그 문서가 서술하는 코드를 열어 확인합니다.
- **제안서 자체 검열 패스**가 추가됐습니다. 제안서를 쓴 뒤 적대적으로 다시 읽어 점수 미달
  항목을 잘라내고, 몇 개를 잘랐는지 보고합니다. 이게 제일 중요합니다 — 12개 중 4개가 부실한
  제안서는 8개짜리 탄탄한 제안서보다 검토 결과가 나쁩니다. 검토자의 의심이 엉뚱한 데 소진되니까요.
- **적용 후 전체 재검증.** 바뀐 문서 전부와 AGENTS.md를 다시 읽어 모순이 생겼는지 확인합니다.
  사실이 새 집으로 옮겨졌는데 옛 요약이 다른 데 살아남는 게 재구성 시의 전형적 사고입니다.

- **실행은 새 세션에서, 보통 두 세션에 걸쳐** 합니다. Pass A(감사·수확·제안서) → 검토 →
  Pass B(적용·검증). Pass B는 제안서를 다시 읽고 시작하므로 깨끗한 컨텍스트에서 돕니다.
  분할 지점이 어차피 승인 경계와 같아서 추가 비용이 없습니다.

바꾸지 **않은** 것도 있습니다. 실행 주기는 여전히 ~5세션입니다. 토큰이 아니라 EK 님의 검토
시간이 병목이라, 매 세션 돌리면 제안서 검토가 부담이 되고 결국 대충 승인하게 됩니다.

## 6. 예산 조정

L0 2,000은 20만 컨텍스트 기준으로 보수적입니다. 그런데 이 숫자는 **지출 한도가 아니라
형태 강제 장치**입니다. AGENTS.md를 포인터 표로 남게 하는 것이 목적이고, 토큰이 싸다는
이유로 완화하면 안 됩니다.

6,000 토큰짜리 AGENTS.md는 감당 가능하지만 여전히 더 나쁩니다. 반드시 지켜야 할 불변 규칙
일곱 줄이, 단지 사실일 뿐인 여러 문단과 같은 지면에서 경쟁하게 되니까요. 늘리더라도
3,000까지만 권합니다.

바꾸려면 두 곳을 같이 고쳐야 합니다:
- `SKILL.md`의 레이어 표와 `references/agents-md-contract.md`의 "Budget enforcement"
- 스크립트 실행 시 `--l0-budget` (또는 스크립트 상단 기본값)

## 7. 사내 모델(GLM 5.2 / Gemma 4) 관련

- 외부 API 호출, 패키지 설치, 네트워크 접근이 전혀 없습니다. Python 3.8+만 있으면 됩니다.
- 스킬 본문은 영어입니다. 지시문은 영어일 때 준수율이 대체로 안정적이지만, 사내 모델이
  한국어에 더 강하다면 번역해도 됩니다. YAML frontmatter의 `name`은 그대로 두세요.

### 구조상 반영해 둔 것

세 가지는 모델 성능과 무관하게 이 스킬의 구조적 요구사항이라 미리 넣어뒀습니다.

1. **SKILL.md만으로 정상 경로가 완결됩니다.** 승격 판정 4기준과 라우팅 표를 본문에 직접
   넣었습니다. 파일 홉이 줄어서 어느 모델에서든 이득입니다. `references/`는 예외 사례와
   포맷 상세를 담은 심화 자료입니다.
2. **`/tune-docs` 커맨드** — 명시 호출용 진입점입니다. 자동 트리거가 붙든 안 붙든 유용합니다.
3. **Step 5의 정지와 Step 7 자체 점검** — "제안서만 쓰고 멈춘다"는 패턴 자체가 흔치 않아서
   명시가 필요합니다. 문서 재구성은 사후 검토가 어려우니 이 단계는 지켜져야 합니다.

### 첫 실행 시 확인할 것

두세 번은 결과를 직접 보시는 걸 권합니다. 어긋날 경우 대처:

| 증상 | 대처 |
|---|---|
| 승인 없이 파일을 고쳐버림 | Step 5 제목을 `### Step 5 — WRITE THE PROPOSAL. THEN STOP.`으로 |
| `references/`를 안 읽음 | 정상입니다. 본문만으로 동작하게 설계했습니다 |
| 스크립트 대신 눈대중으로 토큰 추정 | Step 1에 `Do not estimate token counts by reading files.` 추가 |
| 섹션 G 항목을 직접 적용해버림 | 섹션 G 제목에 `DO NOT APPLY` 강조 |

Gemma 4는 컨텍스트가 GLM보다 짧을 가능성이 높으니, 큐레이션 실행 자체는 GLM 5.2로
돌리는 편이 안전합니다. 감사 스크립트 출력 + 미수확 세션 로그를 한 번에 읽어야 해서
이 스킬은 실행 시점의 컨텍스트 요구가 큰 편입니다.
